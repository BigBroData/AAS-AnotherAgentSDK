# Контракт проекта: Visual Agent Architect (VAA)

## 1. Видение и Цель
**Название:** Visual Agent Architect (VAA)  
**Миссия:** Предоставить инструмент для визуального проектирования, симуляции и исполнения многоуровневых AI-агентов с динамической маршрутизацией запросов.  
**Ключевая ценность:** Объединение интуитивного визуального конструктора (no-code/low-code) с мощным рантайм-движком, поддерживающим адаптивную маршрутизацию на основе условий.

---

## 2. Стек Технологий (Строгое соблюдение)
- **Frontend:** React + Vite (сборка через Bun), xyflow (для графов), Zustand (state management), TailwindCSS (стилизация).
- **Backend/API:** Bun + Hono (высокопроизводительный HTTP-сервер).
- **Runtime Engine:** Кастомный движок на TypeScript (алгоритмы обхода графов, управление состоянием).
- **LLM Integration:** Нативные JS/TS SDK (OpenAI, Anthropic, ollama.js). **Python запрещён.**
- **Формат данных:** JSON/YAML для конфигурации графов.

---

## 3. Архитектура Данных (Core Contract)

### 3.1. Граф (Graph)
Корневой объект, описывающий архитектуру агента.
```json
{
  "id": "string (uuid)",
  "name": "string",
  "version": "string",
  "nodes": ["Node"],
  "edges": ["Edge"],
  "metadata": {
    "createdAt": "ISO8601",
    "updatedAt": "ISO8601",
    "author": "string"
  }
}
```

### 3.2. Узел (Node)
Единица обработки (слой агента).
```typescript
interface Node {
  id: string;
  type: NodeType; // 'llm', 'condition', 'tool', 'input', 'output'
  position: { x: number; y: number }; // Для визуализации
  data: {
    label: string;
    model?: string; // Например, "gpt-4o", "claude-3.5"
    prompt?: string; // Шаблон промпта (может использовать переменные {{variable}})
    systemPrompt?: string;
    parameters?: {
      temperature?: number;
      maxTokens?: number;
      topP?: number;
    };
    toolConfig?: { // Если type === 'tool'
      name: string;
      arguments?: Record<string, any>;
    };
    conditionLogic?: string; // JS-выражение или идентификатор встроенной функции (для type === 'condition')
  };
}
```

### 3.3. Связь (Edge)
Определяет поток данных между узлами.
```typescript
interface Edge {
  id: string;
  source: string; // ID узла-источника
  target: string; // ID узла-назначения
  sourceHandle?: string; // Для поддержки множественных выходов
  targetHandle?: string;
  data?: {
    condition?: string; // Опциональное условие перехода (переопределяет логику источника)
    label?: string;
  };
}
```

### 3.4. Состояние (Execution State)
Объект, передаваемый через граф во время исполнения.
```typescript
interface ExecutionState {
  input: any; // Исходный запрос пользователя
  context: Record<string, any>; // Промежуточные данные, переменные
  history: Array<{ nodeId: string; input: any; output: any; timestamp: ISO8601 }>;
  metadata: {
    startedAt: ISO8601;
    currentPath: string[]; // IDs посещённых узлов
    errors?: Array<{ nodeId: string; error: string }>;
  };
}
```

## 4. API Контракт (Hono Backend)

### 4.1. Управление Графами
- `POST /api/graphs` — Создать новый граф.
- `GET /api/graphs/:id` — Получить граф по ID.
- `PUT /api/graphs/:id` — Обновить граф (полная замена).
- `DELETE /api/graphs/:id` — Удалить граф.
- `GET /api/graphs` — Список всех графов.

### 4.2. Исполнение и Симуляция
- `POST /api/execute` — Запустить исполнение графа.
  ```json
  {
    "graphId": "string",
    "input": "any",
    "mode": "live" | "simulation" // simulation не вызывает реальные LLM, использует моки
  }
  ```
- `WS /api/ws/execute/:sessionId` — WebSocket для стриминга событий исполнения в реальном времени (подсветка узлов, логи).

### 4.3. Валидация
- `POST /api/validate` — Проверить корректность графа (связность, типы узлов, синтаксис условий).

## 5. Логика Движка (Runtime Engine)

### 5.1. Алгоритм Обхода
1. **Старт:** Поиск узла типа `input` или узла без входящих связей.
2. **Обработка:** Выполнение логики узла (вызов LLM, выполнение условия, запуск инструмента).
3. **Маршрутизация:**
   - Если узел имеет исходящие связи, оценка условий (`condition`) на каждой связи.
   - Если условие истинно (или отсутствует), переход к целевому узлу.
   - Поддержка ветвления (параллельное исполнение) и циклов (с защитой от бесконечности).
4. **Завершение:** Достижение узла типа `output` или отсутствие дальнейших путей.

### 5.2. Обработка Условий
- Формат: Строка JavaScript-выражения, имеющая доступ к объекту `state`.
- Пример: `state.context.confidence < 0.8` или `state.output.lastNode.status === 'error'`.
- Безопасность: Использование изолированного контекста выполнения (vm module в Bun) для предотвращения инъекций.

### 5.3. Режим Симуляции
- Заменяет реальные вызовы LLM на предопределённые ответы (mocks).
- Позволяет тестировать логику маршрутизации без затрат на токены.
- Визуализирует путь прохождения данных через граф.

## 6. Frontend Контракт (xyflow)

### 6.1. Кастомные Ноды
- **LLM Node:** Отображает иконку модели, название, превью промпта.
- **Condition Node:** Визуализирует логическое выражение.
- **Tool Node:** Показывает имя инструмента и аргументы.
- **Input/Output Node:** Терминальные точки графа.

### 6.2. Интерактивность
- Перетаскивание узлов, создание связей drag-and-drop.
- Редактирование свойств узла в боковой панели (Properties Panel).
- Кнопка "Run Simulation" с загрузкой тестового input.
- Визуализация потока: анимация прохождения "импульса" по связям во время исполнения.

## 7. Этапы Разработки (Roadmap Summary)
1. **Этап 1: Скелет.** Инициализация репо, настройка Bun, базовый контракт данных, пустые проекты frontend/backend.
2. **Этап 2: Визуальный Редактор.** Интеграция xyflow, создание кастомных нод, сохранение графа в JSON.
3. **Этап 3: Backend API.** Реализация CRUD для графов на Hono, валидация.
4. **Этап 4: Движок Исполнения.** Базовый обход графа, поддержка LLM-узлов (OpenAI), обработка условий.
5. **Этап 5: Симулятор и WebSocket.** Режим моков, стриминг событий на фронтенд, визуализация пути.
6. **Этап 6: Полировка.** UI/UX улучшения, обработка ошибок, документация.

---

## 8. Правила и Ограничения
- **Никакого Python.** Весь код только на TypeScript/JavaScript.
- **DDD Стиль.** Четкое разделение доменной логики (Graph, Node, Engine) от инфраструктуры (API, DB).
- **Типобезопасность.** Использование TypeScript строго, никаких `any` без крайней необходимости.
- **Контракт прежде кода.** Любые изменения в структуре данных сначала обсуждаются и фиксируются в этом документе.
